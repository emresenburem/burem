- Mevcut müşteri, iş, cihaz, fatura, tahsilat ve diğer kayıtları kesinlikle silme.
- Veritabanını sıfırlama, yeniden oluşturma veya seed verileriyle ezme.
- Mevcut çalışan özellikleri bozma.
- Değişiklik öncesinde etkilenecek dosyaların yedeğini al.
- Sahte veri, geçici mock endpoint veya yalnızca görsel çözüm oluşturma.
- Yapılan her değişikliği gerçek API, gerçek PostgreSQL ve gerçek kullanıcı akışıyla test et.
- Uygulamayı sadece Replit üzerinden kullanıyorum; şu anda GitHub veya Render’a bağlı değil.
- Shell üzerinden çalıştırılabilir ve kalıcı çözümler üret.
- Gerekmedikçe yeni paket ekleme.
- İş tamamlanmadan “düzeldi” deme.

1. ÖNCE GİRİŞ SORUNUNU DÜZELT

Şu anda Burem İş Takip’e giriş yapamıyorum.

Aşağıdakileri kontrol et:

- Frontend’in giriş isteğinin hangi endpoint’e gittiği
- API login endpoint’i
- Session oluşturulması
- connect.sid cookie’si
- Express session yapılandırması
- PgSession bağlantısı ve session tablosu
- CORS
- credentials: include
- SameSite
- Secure
- trust proxy
- Replit iframe ve dış adres davranışı
- Frontend ile API proxy yapılandırması
- Port yönlendirmesi
- SESSION_SECRET
- DATABASE_URL
- Kullanıcının gerçekten veritabanında bulunması

Önceden terminal testiyle şu giriş çalışmıştı:

POST /api/auth/login

Gönderilen örnek:

{
  "username": "admin",
  "password": "burem2024"
}

Ve cevap:

{
  "id": 1,
  "username": "admin"
}

Cookie de oluşmuştu. Ancak uygulama arayüzünde şu an giriş yapılamıyor.

Giriş işlemi tamamlandıktan sonra şu endpoint’leri oturumla test et:

- GET /api/auth/me
- GET /api/dashboard/summary
- GET /api/jobs
- GET /api/customers

Başarılı girişten sonra sayfa yenilendiğinde oturum kaybolmamalı.

Not: Kaynak kodda düz metin parola tutma. Mevcut parola sistemi zayıfsa veriyi bozmadan güvenli parola doğrulamasına geçir.

2. REPLIT ÇALIŞTIRMA YAPISINI DÜZELT

Şu anda frontend ve API ayrı ayrı elle çalıştırıldığı için:

- 502 hatası
- Port kullanımda hatası
- Siyah ekran
- Preview bekleme ekranı
- API’nin eski build ile çalışması
- Süreçlerin iki defa başlaması

gibi sorunlar yaşanıyor.

Tek bir kalıcı Replit workflow oluştur veya mevcut “Project” workflow’unu düzelt.

Hedef:

- Run butonuna bir kez basıldığında frontend ve API birlikte başlasın.
- Aynı süreç iki kez başlamasın.
- Eski süreçler temiz biçimde sonlandırılsın.
- Ctrl+C ile tüm alt süreçler kapansın.
- Frontend doğru Replit portunda dinlesin.
- API frontend tarafından erişilebilir olsun.
- Replit dış adresinde `/giris`, uygulama sayfaları ve `/api/*` endpoint’leri birlikte çalışsın.
- Kullanıcının elle PORT=3001 ve PORT=25816 yazmasına gerek kalmasın.
- API kodu değiştiğinde eski dist/index.mjs kullanılmasın; gerekiyorsa yeniden build edilsin.

Gerekirse kökte güvenli bir start script oluştur. Script:

- set -euo pipefail kullansın
- gerekli environment variable’ları kontrol etsin
- child process PID’lerini takip etsin
- trap ile süreçleri kapatsın
- port kullanım hatalarını anlaşılır biçimde göstersin
- rastgele çalışan başka süreçleri öldürmesin

Mockup sandbox üretim akışı için gerekli değilse otomatik çalıştırma.

4. SERVİS TAKİP SORUNUNU KALICI DÜZELT

İş Takip kayıtları için takip numarası şu formatta üretiliyor:

BRM-2026-000041

İş ID’sinden üreten fonksiyon daha önce şöyleydi:

function getTrackingNo(jobId: number): string {
  return `BRM-${new Date().getFullYear()}-${String(jobId).padStart(6, "0")}`;
}

İş Takip’e daha önce şu public endpoint eklendi:

GET /api/public/service-query?q=BRM-2026-000041

Dosya:

artifacts/api-server/src/routes/public.ts

Bu endpoint lokal API’de çalıştı:

http://127.0.0.1:3001/api/public/service-query?q=BRM-2026-000041

ve 200 OK ile kayıt döndürdü.

Fakat Replit dış adresinden aynı endpoint daha önce 502 verdi. Bunun gerçek sebebini çöz. Sadece local çalışan çözüm bırakma.

Endpoint şu iki formatı kabul edebilir:

- BRM-2026-000041
- BRM-000041

Ancak cevapta her zaman standart formatı kullan:

BRM-YYYY-XXXXXX

Yıl değerini sorgu anındaki güncel yıldan körlemesine üretme. Mümkünse işin oluşturulma yılını kullan. Takip numarası gelecekte yıl değiştiğinde bozulmamalı.

Takip numarasından iş ID’si çıkarılırken:

- Sadece geçerli format kabul edilsin.
- Negatif, sıfır, NaN ve aşırı büyük değerler reddedilsin.
- Silinmiş işler bulunmasın.
- Silinmiş müşteriler bulunmasın.
- SQL injection’a açık kod yazılmasın.

5. MÜŞTERİYE TEKNİK DETAY GÖSTERME

Bu kesin bir iş kuralıdır.

Public servis takip endpoint’i müşteriye yalnızca şunları döndürebilir:

- trackingNo
- customerName
- deviceModel veya genel cihaz adı
- genel servis durumu
- createdAt
- updatedAt
- müşteriye özel, genel açıklama varsa sadece o alan

Kesinlikle döndürülmemesi gereken alanlar:

- technicianNote
- notes
- faultDescription içindeki teknik ayrıntılar
- workDescription
- partsUsed
- değişen parçalar
- parça kodları
- yapılan ölçümler
- arızanın gerçek sebebi
- uygulanan onarım yöntemi
- parça maliyetleri
- işçilik maliyeti
- kâr
- iç fotoğraflar
- tedarikçi bilgileri
- kullanıcı veya personel iç notları

Şu anda public endpoint cevabında yanlışlıkla:

technicianNote: jobsTable.notes

kullanılmış olabilir. Bunu tamamen kaldır. Alanı null döndürmek yerine mümkünse API cevabından hiç çıkar.

Müşteriye gösterilecek durumlar genel ve ticari sır içermeyen biçimde olsun:

1: Teslim Alındı
2: İnceleme Yapılıyor
3: Onay Bekleniyor
4: Onarım Sürecinde
5: Test Ediliyor
6: Teslime Hazır
7: Teslim Edildi

İş Takip içindeki mevcut jobStatus değerlerinin tamamını bu genel durumlara doğru eşleştir. Örneğin:

- new, received, accepted → 1
- inspection, examining, diagnosis, fault_detection → 2
- quote, quote_ready, quote_pending, approval_pending, waiting_approval → 3
- repair, repairing, in_repair, in_progress, approved → 4
- test, testing, in_test → 5
- completed, repaired, repair_completed, ready_for_delivery, invoiced → 6
- delivered → 7

Bilinmeyen durumlarda güvenli varsayılan kullan ama hata logla.

6. WEB SİTESİ SERVİS TAKİP ENTEGRASYONU

Web sitesi ayrı bir Replit projesidir. Bu agent yalnızca mevcut İş Takip projesine erişiyorsa, İş Takip tarafını tamamen hazırla ve web sitesinde yapılması gereken değişikliği açık bir patch veya shell komutu olarak raporla.

Web sitesindeki mevcut ekran:

client/src/pages/takip.tsx

Şu endpoint’i çağırıyor:

GET /api/service/query?q=...

Web sitesindeki eski backend route’u daha önce kendi service_records tablosunu sorguluyordu. Sonra Burem İş Takip dış URL’sine yönlendirilecek şekilde değiştirildi.

Kalıcı ve güvenilir mimariyi belirle:

Tercih sırası:

1. Replit dış adresi üzerinden güvenilir public API erişimi gerçekten çalışıyorsa web sitesi bu endpoint’i kullansın.
2. Dış Replit geliştirme adresi kararsızsa, iki uygulamanın aynı PostgreSQL veritabanını kullanması halinde web sitesi yalnızca güvenli alanları doğrudan veritabanından sorgulasın.
3. Geliştirme amaçlı geçici `*.replit.dev` adresini canlı sistemin kalıcı bağımlılığı yapma.

Hangi yöntemin kullanıldığını açıkça raporla.

Web sitesine uygulanacak çözüm, teknik notları kesinlikle döndürmemeli.

7. PERFORMANS SORUNUNU İNCELE

İş Takip yavaş çalışıyor.

Önceden ölçülenler:

- RAM yeterliydi.
- CPU düşük kullanımdı.
- Replit dış adresi ilk veriyi yaklaşık 0.12 saniyede veriyordu.
- Frontend ana JS paketi yaklaşık 1.50 MB idi.
- Büyük PNG dosyaları 0.8 MB civarındaydı.
- Veritabanı Frankfurt Render PostgreSQL üzerindeydi.
- Dashboard summary endpoint’i çok sayıda sorgu ve liste döndürüyor olabilir.
- mockup-sandbox gereksiz yere çalışıyordu.

Şunları ölç:

- Login süresi
- `/api/auth/me` süresi
- `/api/dashboard/summary` süresi
- `/api/jobs` süresi
- PostgreSQL bağlantı süresi
- En yavaş SQL sorguları
- İlk frontend yükleme süresi
- JS ve görsel boyutları

Sonra güvenli optimizasyonlar yap:

- Gereksiz çalışan mockup-sandbox sürecini kaldır.
- Dashboard’da yalnızca gereken kolonları çek.
- Liste limitlerini uygula.
- N+1 sorguları kaldır.
- Gerekli veritabanı indexlerini migration ile ekle.
- Frontend sayfalarını lazy-load et.
- Ağır bileşenleri dynamic import ile böl.
- Büyük görselleri optimize et ama logoyu görsel olarak bozma.
- Gereksiz tekrar sorguları ve kısa cache sürelerini düzelt.
- React Query kullanımını kontrol et.
